# Dossier de continuité du projet API## Objectif du projetCréer une API portable de vente et de livraison de produits numériques, reliée à WhatsApp et à un ou plusieurs prestataires de paiement. L’objectif est de permettre à un vendeur de présenter une offre, échanger avec un prospect, recevoir le paiement, livrer automatiquement le produit numérique et suivre la conversion.Le projet ne doit pas dépendre d’un seul assistant, d’un seul abonnement ou d’une seule plateforme de développement.## Principe de continuitéLe code et les documents doivent appartenir au propriétaire du projet et être conservés dans un dépôt Git indépendant, par exemple GitHub ou GitLab. Les assistants comme Manus ou Claude doivent uniquement aider à lire, écrire, tester et documenter le projet. Aucun assistant ne doit être considéré comme le lieu unique où le projet existe.Les éléments à conserver séparément sont : le code source, la documentation, la spécification OpenAPI, les migrations de base de données, le fichier `.env.example`, les scripts d’installation, les tests, les captures importantes et l’historique des décisions. Les vraies clés secrètes ne doivent jamais être écrites dans le dépôt ; elles doivent rester dans un gestionnaire de secrets ou dans les variables d’environnement de l’hébergeur.## Architecture portable à privilégierLe service doit être construit comme une API HTTP standard, avec une documentation OpenAPI et des endpoints indépendants de Manus. Le projet doit pouvoir être lancé localement avec une commande claire, puis déplacé vers un autre hébergeur sans réécriture importante.Une architecture raisonnable est composée d’un serveur API, d’une base de données relationnelle, d’un stockage privé pour les fichiers numériques, d’un module de paiement, d’un module WhatsApp et d’un module de livraison. Chaque module doit avoir une interface séparée afin de pouvoir remplacer Stripe par un autre prestataire, ou WhatsApp par un autre canal, sans refaire toute l’application.La première version ne doit pas contenir trop de fonctions. Elle doit seulement permettre de créer un produit, créer une offre, générer un lien de paiement, recevoir la confirmation du paiement, livrer un lien sécurisé et consulter l’historique de la commande.## Dépendances externes à isolerWhatsApp Business Platform peut gérer les messages, les médias, les messages interactifs, les modèles et les webhooks. Notre API ne doit donc pas copier WhatsApp ; elle doit simplifier son utilisation pour les vendeurs de produits numériques. Il faudra respecter le consentement des contacts, les modèles approuvés, les règles de messagerie et les coûts de Meta.Le paiement doit être confié à un prestataire établi. Stripe propose notamment Checkout, Payment Links, plusieurs moyens de paiement et des webhooks. L’API ne doit jamais conserver directement les données bancaires. Il faudra vérifier les moyens de paiement disponibles dans chaque pays avant de promettre une couverture internationale.L’intelligence artificielle peut être ajoutée plus tard pour aider à rédiger une description, répondre à des questions fréquentes ou proposer des messages marketing. Elle ne doit pas être indispensable au fonctionnement de base du produit. Le projet doit continuer à fonctionner même si le fournisseur d’IA est remplacé.## Organisation des fichiers à conserver```textapi-produit-digital/├── README.md├── PROJECT_CONTEXT.md├── CHANGELOG.md├── openapi.yaml├── .env.example├── docker-compose.yml├── Dockerfile├── package.json ou pyproject.toml├── src/├── tests/├── migrations/├── docs/│   ├── architecture.md│   ├── api-usage.md│   ├── whatsapp.md│   ├── payments.md│   └── deployment.md└── scripts/```Le fichier `PROJECT_CONTEXT.md` doit expliquer le projet à tout nouvel assistant. Il doit contenir le but, le public visé, ce qui existe déjà, ce qui manque, les décisions prises et la prochaine tâche précise.## Comment continuer avec ClaudeJe peux utiliser Manus pour préparer le cahier des charges, écrire une partie du code, produire la documentation et préparer des fichiers portables. Ensuite, je peux transmettre le dépôt à Claude. Claude devra recevoir le dépôt ou les fichiers nécessaires, lire `PROJECT_CONTEXT.md` et `README.md`, puis travailler par petites étapes. Claude ne doit pas recevoir les clés secrètes réelles. Pour tester, il faut lui donner seulement le fichier `.env.example` avec des valeurs fictives et utiliser des clés de test lorsque les prestataires en fournissent.Chaque session avec Claude doit commencer par une tâche précise, par exemple : « Lis le projet, ne modifie rien, vérifie la structure et donne-moi les trois problèmes les plus importants ». Ensuite, il peut corriger une seule partie, ajouter les tests, mettre à jour la documentation et expliquer les modifications.## Prompt à copier dans Claude> Je poursuis un projet d’API portable de vente et de livraison de produits numériques. Le projet doit rester indépendant de Manus et de tout assistant particulier.>> Lis d’abord `PROJECT_CONTEXT.md`, `README.md`, `openapi.yaml` et la structure du dépôt. Ne modifie aucun fichier avant de me résumer ce que tu as compris.>> Le produit doit permettre à un vendeur de créer un produit numérique, créer une offre, générer un paiement, recevoir la confirmation par webhook, livrer un accès sécurisé et suivre la commande. Une intégration WhatsApp Business et une aide par intelligence artificielle pourront être ajoutées progressivement, mais elles ne doivent pas rendre le cœur de l’API dépendant d’un fournisseur unique.>> Respecte les règles suivantes : ne mets jamais de clé secrète dans le code ; utilise `.env.example` ; écris des tests ; conserve ou mets à jour la documentation OpenAPI ; ne change pas l’architecture sans expliquer pourquoi ; travaille par petites étapes ; indique les fichiers modifiés ; et termine chaque étape par une vérification locale.>> Commence par analyser le dépôt et propose la prochaine tâche la plus utile pour obtenir une première version fonctionnelle.## Plan de travail recommandé1. Valider le besoin avec cinq à dix vendeurs de produits numériques. Il faut leur demander comment ils présentent leur offre, comment ils encaissent, comment ils livrent et à quel endroit ils perdent du temps.2. Définir la première version dans `openapi.yaml` avant de développer. Les premières ressources peuvent être `products`, `offers`, `checkout-sessions`, `orders` et `deliveries`.3. Créer le cœur de l’API sans WhatsApp ni intelligence artificielle : produit, offre, paiement de test, webhook, commande et livraison sécurisée.4. Ajouter un adaptateur de paiement. Le code métier doit dépendre d’une interface interne et non directement de Stripe.5. Ajouter la livraison sécurisée et les protections de base : liens temporaires, expiration, contrôle d’accès et journal des événements.6. Ajouter l’intégration WhatsApp avec quelques modèles approuvés et uniquement pour les contacts ayant donné leur accord.7. Ajouter les statistiques simples : clics, conversations, paiements, livraisons et origine de la vente.8. Tester avec quelques vendeurs réels avant de construire une grande plateforme.## Ce qui peut être gratuit au départLa conception, la documentation, le développement local et les tests peuvent être réalisés sans payer un hébergement permanent. Un ordinateur personnel, un dépôt Git et des services en mode test suffisent pour commencer.Les coûts peuvent apparaître ensuite pour l’hébergement permanent, le nom de domaine, le stockage, les messages WhatsApp, les frais de paiement et l’utilisation d’un service d’intelligence artificielle. Il faut donc repousser ces dépenses jusqu’à ce que le besoin soit validé.## Décision pratiqueLa priorité n’est pas de construire toute l’API immédiatement. La priorité est de créer un dépôt portable, d’y mettre le cahier des charges, puis de développer une petite version qui réalise un seul parcours : créer un produit, générer un paiement de test et livrer le produit après confirmation.De cette manière, le projet pourra être poursuivi ici, avec Claude, sur un ordinateur personnel ou sur un autre hébergeur. Même si un abonnement s’arrête, le projet ne sera pas perdu, car son code, sa documentation et son historique resteront dans le dépôt du propriétaire.## État actuel de la réflexionL’idée recommandée est une API d’orchestration de vente pour produits numériques, centrée sur WhatsApp mais ouverte à plusieurs moyens de paiement. Google Trends a montré un intérêt relatif plus élevé pour « WhatsApp Business » que pour « marketing automation » sous ces formulations exactes. Ces données orientent la recherche, mais elles ne prouvent pas à elles seules la rentabilité. La validation auprès de vendeurs réels reste indispensable.La prochaine décision est de choisir entre deux chemins : préparer d’abord le cahier des charges et le dépôt portable, ou commencer directement le prototype du cœur de l’API en local. Pour limiter les coûts et garder la liberté de passer à Claude, je recommande de commencer par le cahier des charges, la structure du dépôt et un prototype local minimal. ## Sources déjà utilisées- Google Trends : https://trends.google.com/trends/explore?q=WhatsApp%20Business,marketing%20automation,digital%20product,product%20research- Google Trends API : https://developers.google.com/search/blog/2025/07/trends-api- WhatsApp Business Platform : https://developers.facebook.com/documentation/business-messaging/whatsapp/about-the-platform- Stripe Payments : https://docs.stripe.com/payments- Postman State of the API 2025 : https://www.postman.com/state-of-api/2025/
